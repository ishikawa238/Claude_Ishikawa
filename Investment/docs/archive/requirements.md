投資判断支援システム 要件定義書（低コスト・実行規律特化版）

### 1.2 目的

### 1.3 システムの位置づけ
本システムは、全自動売買システムではなく、日次の価格データをもとに高確度の売買パターンを検出し、エントリー・損切り・利確のセットを通知する「実行規律補助システム」である。最終的な投資判断および発注操作は利用者本人が行う。

## 2. 背景

利用者は、日本株と米国株の両方を対象として投資を行いたいと考えている。月次投資可能額は数万円程度であり、システムの月額コストも数千円程度に抑えたい。

### 2.1 コスト回収の考え方
- システムコスト（目安：月3,000円 ※EODHD $19.99/月）を投資リターンで回収することを目標とする
- コスト回収の主な手段は「損切り規律の徹底による損失削減」および「高確度パターンへの集中」とする
- 月次期待値の目標：投資残高に対して月+1〜2%の追加効果（損失削減含む）
- 最初の1年間は期待値の検証フェーズと位置づけ、実績トラッキングで効果を定量評価する

### 2.2 採用方針
- 有料データは価格データ中心に限定する
- テクニカル指標は自前計算する
- 売買パターンを1〜2種類に絞り込み、高確度シグナルに特化する
- ニュース・ファンダメンタル・決算イベントの完全自動化は初期版では行わない
- 市場全体スクリーニングより「実行できる候補の絞り込み」を優先する

## 3. システム目的

本システムの目的は次のとおりである。

1. 日本株および米国株の市場全体から、定義した売買パターンに合致する銘柄を日次で抽出すること
2. 抽出された候補に対してエントリー価格・損切りライン・利確目安・推奨投入額をセットで通知すること
3. 市場全体のトレンド状況を判定し、不適切な局面での新規買いを抑制すること
4. 保有銘柄の損切りライン到達を最優先で通知し、感情的な先送りを防ぐこと
5. 全シグナルの実績を記録し、自分のシグナルの期待値を定量的に把握できるようにすること
6. 朝と夜の2回、実行しやすい形式で通知すること

## 4. 対象範囲

### 4.1 対象市場
- 日本株
- 米国株

### 4.2 対象資産
初期版では普通株を中心とし、以下は原則対象外とする。

- ETF
- REIT
- レバレッジ型商品
- インバース型商品
- 優先株
- OTC銘柄
- 流動性が極端に低い銘柄

### 4.3 利用者像
- 最終判断は自分で行いたい個人投資家
- 損切り規律を機械的に維持したい利用者
- 低コストで投資判断の質と規律を改善したい利用者
- 月次投資可能額が数万円程度の利用者

## 5. システム全体概要

本システムは次の処理を日次で行う。

1. 外部APIから価格データ（個別銘柄・市場インデックス）を取得する
2. データベースに保存する
3. テクニカル指標を計算する
4. 市場環境（インデックスのトレンド）を判定する
5. 流動性フィルタを用いて市場全体を絞り込む
6. 定義した売買パターンに合致する銘柄を抽出する
7. エントリーセット（エントリー価格・損切り・利確・投入額）を計算する
8. 保有銘柄の損切りライン到達判定を行う
9. 朝通知および夜通知を生成する
10. シグナル履歴・通知履歴・実績を保存する

## 6. 基本方針

### 6.1 低コスト運用方針
- データソースは価格データ中心の有料APIを利用する（EODHD EOD Historical Data All World）
- 高価なファンダメンタルAPIやニュースAPIは初期版では採用しない
- テクニカル指標はローカル計算によりコストを抑える
- データベースはSQLiteを採用し、インフラ費を抑える
- 通知はSlack Webhook（無料）を使用する

### 6.2 通知方針
- 夜通知を本判定とする
- 朝通知を要約・行動指示版とする
- 保有銘柄の損切りライン到達通知は最優先で朝通知の先頭に表示する
- 場中のリアルタイム通知は初期版では行わない

### 6.3 投資判断方針
- 短期〜スイングトレード（数日〜数週間）を主軸とする
- 定義した売買パターン以外のシグナルは通知しない
- 売買判断の説明可能性を重視する（なぜそのシグナルが出たかを通知に含める）

### 6.4 売買パターン方針
初期版では以下の2パターンのみを対象とする。他のパターンは検出・通知しない。

#### パターンA：モメンタムブレイクアウト
長期上昇トレンドの継続中に、株価が52週高値を更新し、かつ出来高の急増を伴う状態を検出する。

#### パターンB：押し目買い
長期上昇トレンドの継続中に、一時的な押しから25日移動平均線まで戻った後、反発を確認した状態を検出する。

### 6.5 ポジションサイジング方針
- 1トレードあたりの最大リスク額を総資金の2%に固定する
- 同時保有銘柄数の上限を3銘柄とする
- 推奨投入額はリスク額と損切り幅から逆算して計算する

### 6.6 市場環境方針
- 日経平均・S&P500の両方が25日線を上回っている場合を「通常モード」とする
- いずれか一方でも25日線を下回っている場合を「警戒モード」とする
- 警戒モード中は新規買いシグナルを発信しない（通知に警戒モードである旨を明示する）

## 7. データ要件

### 7.1 利用する外部データ
- 日次バッチの価格データ取得：**EODHD EOD Historical Data**（有料プラン $19.99/月）の Bulk EOD エンドポイントを使用する（1リクエストで取引所全銘柄を取得）
- 初回3年分の一括取得：**yfinance**（非公式 Yahoo Finance API・無料）を使用する。EODHD の日次リクエスト枠を消費しないため初回セットアップに適している
- 日本株の財務データ・決算予定日取得：**J-Quants API**（jquants-api-client v2、無料プランあり）を使用する。月次バッチで `fins/statements`（財務諸表）、夜バッチで `fins/announcement`（決算発表予定）を取得する

### 7.2 自動取得対象（個別銘柄）
- 銘柄コード
- 銘柄名
- 市場区分
- 日足価格（始値・高値・安値・終値）
- 出来高
- 発行済株式数（時価総額計算に使用）

### 7.3 自動取得対象（市場インデックス）
以下の4インデックスを日次で取得する。

| インデックス | 用途 |
|-------------|------|
| 日経平均（N225） | 日本株の市場環境判定 |
| TOPIX（TOPIX.TSE） | 日本株の市場環境判定（補助） |
| S&P500（GSPC.INDX） | 米国株の市場環境判定 |
| NASDAQ（IXIC.INDX） | 米国株の市場環境判定（補助） |

### 7.4 自前計算対象（テクニカル指標）

| 指標 | 定義 |
|------|------|
| 5日移動平均（MA5） | 直近5営業日の終値単純平均 |
| 25日移動平均（MA25） | 直近25営業日の終値単純平均 |
| 75日移動平均（MA75） | 直近75営業日の終値単純平均 |
| 200日移動平均（MA200） | 直近200営業日の終値単純平均 |
| 20日平均出来高 | 直近20営業日の出来高単純平均 |
| 20日高値 | 直近20営業日の終値の最高値 |
| 52週高値 | 直近252営業日の終値の最高値 |
| 52週安値 | 直近252営業日の終値の最低値 |
| 5日騰落率 | （当日終値 - 5営業日前終値）/ 5営業日前終値 × 100 |
| 20日騰落率 | （当日終値 - 20営業日前終値）/ 20営業日前終値 × 100 |
| RSI | 期間14日・Wilder平滑化方式。RSI = 100 - 100/(1 + RS)。RSは14日間の平均上昇幅/平均下降幅 |
| ATR | 期間14日のAverage True Range。True Range = MAX(高値-安値, 高値-前日終値の絶対値, 安値-前日終値の絶対値) |
| ボラティリティ | 直近20営業日の終値対数収益率の標準偏差（年率換算：×√252） |
| 売買代金（推計） | 終値 × 出来高（実際の売買代金が取得できない場合の代替値） |
| 時価総額（推計） | 終値 × 発行済株式数 |

### 7.5 修正株価の扱い
- 株式分割・権利落ちによる価格不連続を防ぐため、取得するデータはEODHDの修正後終値（Adjusted Close）を使用する
- 移動平均・RSI・ATR・ボラティリティはすべて修正後終値で計算する

### 7.6 初期データ取得期間
- システム初回セットアップ時、過去3年分（約756営業日相当）の価格データを一括取得する
- 200日移動平均の計算に最低200日、52週高値の計算に最低252日が必要なため

### 7.7 自動取得対象（財務・決算、JP のみ）
J-Quants API により以下を自動取得する。対象は日本株（JP）のみ。

| データ | 取得元エンドポイント | 更新頻度 |
|--------|-------------------|---------|
| 売上高・営業利益・経常利益・純利益 | `fins/statements` | 月次 |
| EPS（1株当たり利益） | `fins/statements` | 月次 |
| BPS（1株当たり純資産） | `fins/statements` | 月次 |
| 発行済株式数 | `fins/statements` | 月次 |
| 年間配当（1株当たり） | `fins/statements` | 月次 |
| PER・PBR・配当利回り | price_history の最新終値から計算 | 月次 |
| 決算発表予定日 | `fins/announcement` | 夜バッチ（保有銘柄のみ） |

### 7.8 手動または将来拡張対象
- ニュース情報
- セクター別高度分析

## 8. 機能要件

## 8.1 データ取得機能
### 概要
外部APIから日次価格データ・銘柄マスタ情報・市場インデックスデータを取得する。

### 要件
- 日本株および米国株の価格データ（修正後終値含む）を取得できること
- 市場インデックス4本の価格データを取得できること
- 日次で価格更新を行えること
- 銘柄マスタを初回作成および月次更新できること
- API失敗時はリトライを3回実施し、3回失敗した場合は当該銘柄をスキップしてバッチ処理を継続すること
- 取得失敗銘柄数・失敗理由をエラーログに記録し、通知に「データ取得失敗：X件」を含めること
- APIレートリミットを超えないようにリクエスト間隔を調整すること

### バッチ実行タイミング
| 市場 | 夜バッチ実行時刻（日本時間） | 理由 |
|------|--------------------------|------|
| 日本株 | 当日**20:30** | 東証は15:30終了。調整時間を確保 |
| 米国株 | 翌朝**7:30** | NYSEは日本時間翌6:00頃終了 |

- 実装上は米国株含む一括バッチを翌朝7:30に実行し、日本株の朝通知は前日夜バッチ（日本株のみ）の結果を使う2段階構成とする

---

## 8.1.5 J-Quants 財務・決算データ取得機能
### 概要
J-Quants API から日本株の財務データおよび決算発表予定日を取得し、DB に保存する。
対象は JP 銘柄のみ。米国株はこの機能の対象外とする。

### 財務データ取得（月次）
- 月次バッチ（STEP 1.5）で `fins/statements` を銘柄ごとに取得する
- 取得した最新期のデータを `fundamentals_snapshot` テーブルに UPSERT する
- `universe_master.shares_outstanding`（発行済株式数）を最新値で上書き更新する
- PER・PBR・配当利回りは `price_history` の最新終値から計算して保存する
  - PER = 終値 ÷ EPS
  - PBR = 終値 ÷ BPS
  - 配当利回り = 年間配当 ÷ 終値 × 100

### 決算発表予定日取得（夜バッチ）
- 夜バッチ（STEP 7 内）で `fins/announcement` を **1回のリクエストで全銘柄分**取得する
- 取得結果を保有銘柄コードでフィルタし、当日以降の予定のみ `earnings_schedule` テーブルに UPSERT する
- J-Quants の銘柄コードが 5 桁（例: "72030"）の場合、universe_master の 4 桁コード（例: "7203"）と両方で照合する

### 要件
- J-Quants リフレッシュトークンが未設定の場合は警告ログを出力してスキップし、他処理には影響を与えないこと
- API 失敗時は当該銘柄をスキップしてバッチ処理を継続すること
- リクエスト間隔は `config.json` の `jquants.request_interval_sec`（デフォルト 1.0 秒）で調整すること

## 8.2 データ保存機能
### 概要
取得データ・計算結果・判定結果・通知結果を保存する。

### 要件
- SQLiteに価格データを保存できること
- テクニカル指標を保存できること
- 判定履歴・シグナル履歴を保存できること
- 通知本文を保存できること
- 日次でSQLiteファイルをバックアップできること（保存先：同フォルダ内にタイムスタンプ付きファイル名で保存、直近7日分を保持）
- バックアップ失敗時はエラーログに記録すること

## 8.3 テクニカル指標計算機能
### 概要
価格データからテクニカル指標を自動計算する。

### 要件
- 7.4に定義した全指標を算出できること
- 計算に必要なデータが不足している場合（上場直後の銘柄など）はNULLを記録し、スクリーニング対象から除外すること
- 市場インデックス4本についても同様のMA計算を行うこと

## 8.4 市場環境判定機能
### 概要
市場インデックスのトレンドを判定し、新規買いの可否を判断する。

### 判定ロジック

| モード | 条件 | 新規買いシグナル |
|--------|------|----------------|
| 通常モード | 日経平均MA25以上 かつ S&P500MA25以上 | 発信する |
| 警戒モード（一方） | 日経平均またはS&P500のいずれかがMA25未満 | 発信しない。通知に「警戒モード中：〇〇が25日線を割れています」と明示 |
| 警戒モード（両方） | 日経平均およびS&P500の両方がMA25未満 | 発信しない。「全面警戒モード」として通知に赤字（Slackのcolor: danger）で表示 |

### 要件
- 日次で市場環境モードを判定し、market_environment テーブルに保存すること
- 警戒モード中は 8.6 の新規買い候補を通知出力に含めないこと
- 保有銘柄の監視・損切り通知は市場環境に関わらず継続すること

---

## 8.5 市場全体スクリーニング機能
### 概要
市場全体を対象としつつ、流動性の低い銘柄を除外する。

### 要件

#### 日本株フィルタ（全条件必須）
- 株価300円以上
- 終値 × 出来高（推計売買代金）が3億円以上
- 終値 × 発行済株式数（推計時価総額）が300億円以上

#### 米国株フィルタ（全条件必須）
- 株価5ドル以上
- 終値 × 出来高（推計売買代金）が2,000万ドル以上
- 終値 × 発行済株式数（推計時価総額）が20億ドル以上

#### 共通フィルタ
- 直近30営業日のうち取引が存在する日が20日以上であること（非アクティブ銘柄の除外）
- 対象外資産（ETF・REIT等）を除外すること
- MA200が計算可能なこと（上場から200営業日以上経過していること）

## 8.6 新規買い候補判定機能
### 概要
8.4で通常モードと判定された場合のみ、定義した2つの売買パターンに合致する銘柄を抽出する。

### パターンA：モメンタムブレイクアウト 検出条件（全条件必須）

| 条件 | 定義 |
|------|------|
| 長期上昇トレンド | MA200が右肩上がり（当日MA200 > 5営業日前MA200） |
| 中期上昇トレンド | MA75がMA200以上 |
| 短期上昇トレンド | MA25がMA75以上 かつ MA5がMA25以上 |
| 52週高値更新 | 当日終値が52週高値の95%以上 |
| 出来高急増 | 当日出来高が20日平均出来高の1.5倍以上 |
| RSI条件 | RSIが50以上70未満（強気だが過熱なし） |
| 株価水準 | 終値がMA25以上 |

### パターンB：押し目買い 検出条件（全条件必須）

| 条件 | 定義 |
|------|------|
| 長期上昇トレンド | MA200が右肩上がり（当日MA200 > 5営業日前MA200） |
| 中期上昇トレンド | MA75がMA200以上 |
| 押し目からの反発 | 直近5営業日以内にMA25タッチ（安値がMA25の98%以下）があり、当日終値がMA25以上 |
| 出来高の回復 | 当日出来高が20日平均出来高の0.8倍以上（急増は必須としない） |
| RSI条件 | RSIが40以上60以下（過熱なし・売られすぎなし） |
| MA25の安定性 | MA25が右肩上がり（当日MA25 > 5営業日前MA25） |

### 通知件数
- 各パターンで上位3件まで（合計最大6件）
- ランク付けは「当日出来高 ÷ 20日平均出来高」の比率が高い順とする

### シグナルラベル

| ラベル（内部値） | 意味 |
|----------------|------|
| 実行候補（`candidate`） | 全条件を満たす。翌営業日のエントリーを推奨。エントリーセットを付与 |
| 保留（`watch`） | パターンに準じるが全条件を満たさない（参考表示のみ、エントリーセットなし） |
| 対象外（`skip`） | 明確に条件を満たさない。記録のみ、通知には含めない |

### 要件
- 各銘柄に該当パターン名・ラベルを付与できること
- どの条件を満たし、どの条件が不足しているかを記録できること
- 「実行候補」ラベルの銘柄にはエントリーセットを計算すること（8.10参照）

## 8.7 保有銘柄判定機能
### 概要
保有銘柄に対して継続保有・売り検討・強制損切りを判定する。

### 保有銘柄の管理方法
- 保有銘柄情報は利用者がCSVファイルまたはJSON形式で手動入力する
- 保有銘柄登録時に取得単価・取得日・損切りライン（任意）を記録する
- 損切りラインが未入力の場合は取得単価の-8%を自動設定する

#### 保有銘柄CSVフォーマット（初期版）
```
ticker,name,market,entry_price,entry_date,quantity,stop_loss_price,memo
7203,トヨタ自動車,JP,3200,2025-01-15,100,2944,
AAPL,Apple Inc,US,185.5,2025-01-20,10,,
```

### 判定ロジック

| ラベル | 条件 | 通知での扱い |
|--------|------|------------|
| 強制損切り | 終値が損切りラインを下回った | 朝通知の最先頭に赤字（danger）で表示。「翌朝寄付での手仕舞いを推奨」と明記 |
| 損切りライン接近 | 終値が損切りラインの2%以内 | 朝通知の上位に警告色（warning）で表示 |
| 売り検討 | 下記条件のいずれかを満たす | 夜通知に記載 |
| 継続保有 | 上記以外 | 夜通知に一覧記載 |

#### 売り検討条件（いずれか1つ以上で該当）
- MA5がMA25を下抜けた（当日MA5 < MA25 かつ 前日MA5 >= MA25）
- 終値がMA25を5%以上下回った
- 損益率が-5%以下（損切りライン到達前の早期警戒）
- 取得後20営業日以内に損益率が+10%以上到達後、当日損益率が+5%以下に低下

### 決算アラート判定（JP 銘柄のみ）
`earnings_schedule` テーブルを参照し、保有銘柄の直近決算発表予定日までの残り日数を判定する。

| 残り日数 | アラートレベル | 表示 |
|---------|--------------|------|
| 3日以内 | critical | 🚨 で強調表示 |
| 7日以内 | warning | ⚠️ で表示 |
| 8日以上または未登録 | なし | 表示しない |

- 閾値は `config.json` の `jquants.earnings_alert_days_critical`（デフォルト 3）および `jquants.earnings_alert_days_warning`（デフォルト 7）で設定する
- 決算アラートは朝通知・夜通知の両方に「📅 決算アラート」セクションとして表示する

### 要件
- 保有銘柄CSVを日次バッチ実行時に自動読み込みできること
- 保有銘柄ごとに現在損益率・損益額を計算して通知に含めること
- 強制損切り判定は市場環境モードに関わらず実行すること
- JP 保有銘柄の決算アラートを判定し、閾値以内の場合は通知に含めること
- `earnings_schedule` にデータがない場合（J-Quants 未設定・未取得）は決算アラートを表示しないこと

## 8.8 朝通知機能
### 概要
その日の行動前に確認するための行動指示型通知を生成する。

### 含める内容・表示順序（上から優先度順）

1. **【要即時対応】強制損切り対象銘柄**（ある場合のみ、赤字・danger表示）
2. 市場環境モード（通常 / 警戒 / 全面警戒）とインデックス状況
3. 損切りライン接近銘柄の警告（ある場合のみ）
4. 今日の買い候補（通常モード時のみ）：最大2件、エントリーセット付き
5. 保有銘柄要約（継続保有件数・要注意件数）
6. **📅 決算アラート**（JP 保有銘柄で閾値以内の決算がある場合のみ）

### 要件
- 1分程度で読める文章量であること
- 強制損切り対象がある場合は必ず先頭に表示し、他の情報より視覚的に目立たせること
- 買い候補にはエントリーセット（エントリー価格・損切り・利確・推奨投入額）を含めること
- 朝通知生成時刻：日本株は当日8:00、米国株を含む場合は当日7:30（翌朝バッチ後）

## 8.10 エントリーセット計算機能
### 概要
「実行候補」ラベルが付与された銘柄に対して、エントリーに必要な情報を一括計算する。

### 計算ロジック

| 項目 | 計算方法 |
|------|---------|
| エントリー価格目安 | 当日終値（翌日寄付での執行を想定） |
| 損切りライン | エントリー価格 - (ATR × 2)。ただし最小値として取得単価の-8%も参照 |
| 損切り幅（%） | （エントリー価格 - 損切りライン）/ エントリー価格 × 100 |
| 利確目安 | エントリー価格 × (1 + 損切り幅(%) × 2)（リスクリワード2:1） |
| 推奨投入額 | 総資金 × 0.02 / 損切り幅(%)（1トレードの最大リスク = 総資金の2%） |
| 最大同時保有数 | 3銘柄（超える場合は投入額を減額するか見送りを検討） |

- 総資金は利用者が設定ファイル（config.json）に手動で入力する
- 損切り幅が1%未満の場合は「損切り幅が狭すぎます」と警告し、エントリーを推奨しない
- 損切り幅が15%超の場合は「損切り幅が広すぎます。ボラティリティが高い銘柄です」と警告する

### 要件
- 「実行候補」ラベルの全銘柄にエントリーセットを計算できること
- 推奨投入額が1単元（日本株）または最低取引単位（米国株）を下回る場合は「投資金額に対して銘柄単価が高すぎます」と警告すること

## 8.11 実績トラッキング機能
### 概要
システムが発したシグナルの実績を記録し、期待値を定量評価できるようにする。

### 記録の流れ
1. システムがシグナルを発信した時点で `trade_signal_log` テーブルに自動記録する
2. 利用者は実際にエントリーした場合・決済した場合に、手動でCSVを更新するかコマンドで記録する
3. 月次集計レポートをコマンドで生成できる

### 月次集計レポートの内容
| 指標 | 算出方法 |
|------|---------|
| シグナル数 | 月間に「実行候補」が出た件数 |
| 実行数 | 実際にエントリーした件数 |
| 実行率 | 実行数 / シグナル数 × 100 |
| 勝率 | 利益確定決済数 / 決済済み件数 × 100 |
| 平均利益（%） | 利益確定トレードの平均損益率 |
| 平均損失（%） | 損失確定トレードの平均損益率 |
| 期待値（%/トレード） | 勝率×平均利益 + 負率×平均損失 |
| パターン別勝率 | パターンAとパターンBを分けて集計 |
| 市場別勝率 | 日本株・米国株を分けて集計 |

### 要件
- シグナル発信時に自動記録できること
- エントリー・決済情報の手動入力を受け付けられること
- 月次集計レポートをコマンドライン実行で出力できること
- 集計に最低10件のサンプルがない場合は「サンプル数不足：統計的信頼性が低いです」と警告すること

## 8.12 moomoo 保有銘柄同期機能（任意）
### 概要
moomoo OpenD が起動中の場合、バッチ実行時に保有銘柄と約定履歴を自動同期する。moomoo 未接続でも `holdings.csv` による手動管理で動作するため、本機能は任意である。

### 機能

| 機能 | 内容 |
|------|------|
| 保有銘柄同期 | moomoo OpenD から JP/US の現在ポジションを取得し `holdings.csv` とマージ |
| 約定履歴同期 | 過去90日の約定履歴を取得し、BUY/SELL を自動ペアリングして `trade_result_log` に記録 |

### 処理フロー
1. 夜バッチ・朝バッチの実行時に `moomoo_sync.sync_from_moomoo()` を呼び出す
2. moomoo OpenD に TCP 接続し、現在のポジション一覧を取得する
3. 既存の `holdings.csv` とマージする（既存行の stop_loss_price・memo は保持）
4. `moomoo_sync.sync_trade_results()` で約定履歴を取得し、`trade_result_log` に記録する
5. 対応するシグナルがない場合は手動エントリーとして自動作成する

### 要件
- moomoo OpenD 未接続時はスキップし、バッチ処理を継続すること
- 既存の `holdings.csv` の手動設定値（stop_loss_price, memo）を上書きしないこと
- `config.json` に `moomoo` セクションがない場合は同期をスキップすること

## 9. 非機能要件

### 9.1 コスト要件
- 月額コストは数千円程度（目安：5,000円以内）に抑えること（現在：EODHD $19.99/月 ≈ 3,000円、Slack 無料）
- 初期版では高価なファンダメンタルAPIを採用しないこと
- ローカル実行を前提とし、クラウド費用を極力発生させないこと

### 9.2 性能要件
- 日本株の夜バッチ（20:30実行）が21:00までに完了すること
- 翌朝の米国株含む一括バッチ（7:30実行）が8:00までに完了すること
- 処理対象銘柄数の目安：日本株4,000銘柄・米国株8,000銘柄（フィルタ後200〜500銘柄程度）

### 9.3 可用性要件
- 一部データ取得に失敗しても全体が停止しにくい構成であること
- エラーログをファイルに保存できること
- DBバックアップが失敗しても本体処理を継続すること

### 9.4 保守性要件
- モジュール分割された構成であること
- 売買パターンの条件を設定ファイルまたはコード上の定数として変更しやすい構成にすること
- 将来的にファンダメンタルやニュース機能を追加しやすいこと

### 9.5 説明可能性要件
- 判定ラベルに加え、どの条件を満たし・どの条件を満たさなかったかを記録・通知すること
- 月次集計レポートでシグナルの期待値を定量的に確認できること

### 9.6 データ整合性要件
- 修正後株価のみを指標計算に使用すること
- 市場休場日（日本・米国の祝日・年末年始等）はデータ取得をスキップし、休場フラグをDBに記録すること
- 上場廃止銘柄を保有している場合は「上場廃止フラグ」を立て、通知で警告すること

- moomoo 連携は保有銘柄同期と約定履歴取得のみ。moomoo OpenD 未接続でも動作する
- 初期版では場中リアルタイム判定を行わない
- 売買パターンはA（モメンタムブレイクアウト）・B（押し目買い）の2種類のみとし、他のパターンは初期版では追加しない
- コスト優先のため、機能よりも運用継続性と安定性を重視する

## 16. 受け入れ基準

本システムの初期版は、少なくとも次を満たした場合に受け入れ可能とする。

1. 日本株・米国株の価格データ（修正後終値）を日次で取得できること
2. 市場インデックス4本のデータを取得し、市場環境モードを判定できること
3. テクニカル指標（MA・RSI・ATR等）を自動計算できること
4. 流動性フィルタを通過した銘柄に対して2パターンの検出を実行できること
5. 「実行候補」ラベルの銘柄にエントリーセット（エントリー・損切り・利確・投入額）を計算できること
6. 保有銘柄の損切りライン到達を判定し、朝通知の先頭に警告表示できること
7. Slackへの朝通知・夜通知を自動生成・送信できること
8. シグナル発信ごとにtrade_signal_logに自動記録できること
9. 月次集計レポートをコマンドで生成できること
10. 月額コストが5,000円以内に収まること

## 18. まとめ

本システムは、低コストで継続的に利用できることを前提としつつ、**感情的な損切り遅延の防止**と**高確度パターンへの集中**によって投資成果の改善を目指す実行規律補助システムである。

初期版では2つの売買パターン（モメンタムブレイクアウト・押し目買い）に特化し、通知をエントリーセット付きの少件数（最大3〜6件）に絞り込むことで、「通知を受け取って実際に行動できる」システムを目指す。

実績トラッキング機能により、1年間でシグナルの期待値を定量評価し、効果が確認できたパターンはそのまま継続、効果が低いパターンは条件を見直すPDCAを回す。

今後は、本要件定義書をもとに、詳細設計・DB定義・バッチ仕様・通知テンプレートへと具体化していく。
