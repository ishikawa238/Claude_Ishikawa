# 投資委員会（マルチエージェント判断支援）要件定義

> **免責**: 本機能は投資助言や利益保証を行うものではありません。委員会の判定は「検討材料」であり、注文指示ではありません。最終的な売買判断はユーザー自身の責任で行ってください。

作成日: 2026-09-24
ステータス: Phase 1 実装済み（2026-09-24、`committee.enabled=false` 既定）。実装は `investment_support/src/committee.py` / `committee_prompts.py` / `fundamentals_fetcher.py`

---

## 1. 背景と目的

### 1.1 背景

- 既存の `llm_advisor.py` は、同一プロンプトを OpenAI / Anthropic / Gemini に並列送信し、単一ペルソナ（投資教育アシスタント）の所感を Slack に載せている。
- `memo.txt` の拡張案「異なるペルソナを与えたエージェントの意見を定期通知に加える」の発展形として、運用会社の**投資委員会**を模した複数エージェントの議論で判断品質を高める。

### 1.2 目的

1. 単一 LLM のバイアス・ハルシネーションを、役割の異なる複数エージェントの**独立意見 + 反論**で抑える。
2. 既存シグナルに対する「GO / NO-GO」フィルタとして機能し、判断品質を高める。
3. 効果を**計測可能**にし、月額運用費に対して価値があるかを数字で判断できるようにする。

### 1.3 「コスト回収」の定義

運用資金は 50 万円未満のため、絶対リターンでの回収判断は現実的でない。以下を成功基準とする。

| KPI | 目標 | 計測方法 |
|-----|------|---------|
| 判断品質 | 委員会 GO 銘柄のペーパートレード期待値 ＞ 全シグナルの期待値 | `paper_trades` を委員会判定でグルーピングし、3 か月（約 60 営業日）で比較 |
| 運用費 | LLM API 費 **1,000 円/月以下** | `committee_verdict_log` の推定コスト合計 |
| 稼働率 | 委員会開催率 90% 以上、エージェント欠席率 10% 以下 | `committee_verdict_log.status` |

## 2. 確定した設計判断

| 項目 | 決定 | 理由 |
|------|------|------|
| 配置 | Investment の拡張。`llm_advisor` を委員会に置き換える | データ配管・通知・保存・評価基盤が既にある |
| 対象銘柄 | 当日の買い候補（entry_sets）+ 売り検討/損切り接近の保有銘柄 | コストが銘柄数に比例するため上限を自然に抑えられる |
| 月額予算 | 1,000 円/月（日次ガード約 45 円） | 資金規模に見合う水準 |
| ディベート | 固定 2 ラウンド（独立意見 → リスク反論 + 応答 → PM 判定） | コストが予測可能。往復増は同調しやすく効果が薄い |
| 実装方式 | 自前の軽量オーケストレーション（`requests` ベース） | 既存コードと同じ依存構成。フレームワークはトークン消費が見えにくい |
| 財務データ | yfinance の財務情報（無料・非公式） | PoC 向け。JP は J-Quants があれば優先 |
| 出力 | Slack に結論サマリー、ダッシュボードに議事録全文 | Slack のセクション上限（3,000 文字）対策 |

## 3. スコープ

### 3.1 対象

- **買い候補**: `entry_calculator` が算出した entry_sets（`signal.max_entry_sets_per_batch` 件、既定 3）
- **保有銘柄**: `holdings_monitor` の判定ラベルが `sell_watch` または `sl_near` のもの
- **実行タイミング**: 朝バッチ（07:30, US）・夜バッチ（20:30, JP）の現 `llm_advisor` 呼び出し位置（STEP 7.5）

### 3.2 非スコープ（Phase 1 では扱わない）

- 自動発注、リアルタイム/分足データ
- バックテスト（LLM は過去を知っているため look-ahead バイアスを排除できない。評価は前向きペーパートレードのみ）
- オンデマンド実行（Prompt Builder 連携）→ Phase 3 で検討
- 数百銘柄の一括スキャン

### 3.3 委員会が上書きしないルール

以下は既存のルールベース判定を優先し、委員会は意見を述べるだけで結論を変えない。

- 損切りライン到達（`forced_stop`）
- `risk_control` による新規買い停止（月間損失・連続損失）
- 市場環境 `caution` / `full_caution` 時の新規買い停止（candidate は既に watch に降格済み）

## 4. エージェント定義

全エージェントは**計算済みの数値を解釈する**役割に限定し、LLM に指標計算をさせない。

| エージェント | 入力（既存モジュール） | 役割 | モデル層 |
|-------------|----------------------|------|---------|
| ファンダメンタル・アナリスト | yfinance 財務（PER/PBR/ROE/売上成長率/営業利益率/負債比率）、JP は `fundamentals_snapshot` 優先 | 企業価値・割安/割高の評価 | 軽量 |
| テクニカル・アナリスト | `technical_snapshot`（MA/EMA/RSI/MACD/ATR/出来高比/52 週高値距離）、`conditions_met` | 売買タイミングの評価 | 軽量 |
| マクロエコノミスト | `index_snapshot`（N225/SP500 と MA 比）、`market_environment` 推移、USD/JPY、`fetch_market_news` | マクロ環境の追い風/逆風 | 軽量 |
| リスク・マネージャー（悪魔の代弁者） | `risk.py`（VaR/Beta/Sharpe）、損切り幅、ATR、決算接近、ポートフォリオ集中度、Round 1 の 3 意見 | 強気意見への反論、ダウンサイドの指摘 | 軽量 |
| ポートフォリオ・マネージャー | 全意見 + 反論 + 応答 + エントリーセット | 最終判定と根拠、少数意見の記録 | 高性能 |

- **マクロ概況は 1 バッチにつき 1 回だけ生成**し、全銘柄で共有する（銘柄数に比例しない）。
- モデルは `config.json > committee.agents.<name>.provider / model` で差し替え可能にする。モデル名は資料日付で陳腐化するため、コードに固定しない。

### 4.1 各アナリストの出力スキーマ（JSON）

```json
{
  "stance": "bullish | neutral | bearish",
  "confidence": 0.0,
  "key_points": ["...", "...", "..."],
  "risks": ["...", "..."],
  "summary": "200 文字以内"
}
```

### 4.2 PM の出力スキーマ（JSON）

```json
{
  "verdict": "BUY | WAIT | SKIP",
  "confidence": 0.0,
  "position_size_adj": "full | half | skip",
  "rationale": "300 文字以内",
  "dissent": "少数意見の要約（100 文字以内）",
  "absent_agents": []
}
```

保有銘柄の場合の `verdict` は `HOLD | REDUCE | SELL`、`position_size_adj` は `keep | half | exit`。
許可されていない判定語は JSON 解析失敗と同じ扱い（1 回再要求 → 失敗なら `failed`）。

## 5. ディベート・プロトコル

```
[バッチ開始時 1 回] マクロ概況生成（マクロエコノミスト）
        ↓
[銘柄ごと]
Round 1: ファンダ / テクニカル / リスク（初期評価）を並列実行
         ※互いの出力は渡さない（アンカリング防止）
        ↓
Round 2: リスク・マネージャーが Round 1 の強気論点に反論（1 回）
        ↓
         反論対象になったアナリストのみ 1 回応答（150 文字以内）
        ↓
PM: 全材料から JSON 判定
```

- LLM 呼び出し回数: 銘柄あたり最大 **8 回**（3 + 1 + 最大 3 + 1）+ バッチあたりマクロ 1 回
- 反論対象がいない（全員 neutral/bearish）場合は応答をスキップし、コストを節約する
- 並列実行は既存 `llm_advisor` と同じ `ThreadPoolExecutor` パターンを使う

## 6. コストと予算ガード

### 6.1 概算

前提（モデル価格は変動するため `config.json > committee.pricing` に持たせ、ログにはこの単価で推定コストを保存する）:

- 軽量モデル呼び出し: 入力約 3,000 トークン + 出力約 400 トークン → 数円未満
- PM（高性能）呼び出し: 入力約 6,000 トークン + 出力約 600 トークン → 数円
- **銘柄あたり概算 8〜12 円**、1 日 4〜5 銘柄で **月 1,000 円前後**

### 6.2 予算ガード

- 日次予算 `committee.daily_budget_jpy`（既定 45 円）。当日の推定コスト合計が超えたら残りの銘柄をスキップし、Slack に「予算上限のため未審議」と明記する。
- 審議の優先順位: **保有銘柄の売り検討/損切り接近 → 買い候補をスコア降順**（資金がすでに入っているものを優先）。
- プロンプトのトークン推計は既存 `_estimate_tokens` を流用し、上限超過時はニュース → 財務詳細の順に削る。
- 同日・同バッチ・同銘柄の判定はキャッシュし、再実行時に API を呼ばない（既存 `llm_feedback_log` のキャッシュ方式に準じる）。

## 7. データ

### 7.1 新規テーブル

**`committee_verdict_log`** — 判定 1 件 = 1 行

| カラム | 内容 |
|--------|------|
| `id`, `verdict_date`, `batch_type` | 主キー・実行日・morning/evening_jp |
| `ticker`, `market`, `subject_type` | 銘柄・市場・`buy_candidate` / `holding` |
| `verdict`, `confidence`, `position_size_adj` | PM 判定 |
| `pm_rationale`, `dissent` | 根拠と少数意見 |
| `agents_json` | 各エージェントの出力・反論・応答（JSON 全文） |
| `prompt_tokens`, `output_tokens`, `estimated_cost_jpy`, `latency_ms` | コスト計測 |
| `status` | `full` / `partial`（欠席あり）/ `skipped_budget` / `failed` |

**`committee_macro_brief`** — バッチごとのマクロ概況キャッシュ（`brief_date`, `batch_type`, `text`, tokens）

**`fundamentals_cache`** — yfinance 財務情報の日次キャッシュ（`ticker`, `fetched_date`, `data_json`）。取得失敗時は前日キャッシュを使い、ファンダ・アナリストに「データ鮮度」を明記して渡す。

### 7.2 既存テーブルへの追加

- `paper_trades` に `committee_verdict` / `committee_confidence` カラムを追加（`init_db.py` の `MIGRATION_STATEMENTS` に冪等に追加）。
- `update_paper_trades --summary` に委員会判定別の期待値・勝率・件数の内訳を追加する。これが KPI 1 の計測手段になる。

## 8. 出力

### 8.1 Slack（朝・夜通知内）

- 銘柄ごとに 1〜2 行: `判定 / 確信度 / 根拠の一文 / 少数意見の一文`
- 欠席エージェント・予算スキップがあれば明記
- ダッシュボードの議事録ページへのリンク
- 既存ルールに従い、視覚的に分かりやすく楽しい構成にする（絵文字で判定を色分けする等）

### 8.2 ダッシュボード

- 新規ページ `/committee`（`order_server.py` に追加）: 日付ごとの判定一覧、行を展開すると各エージェントの意見・反論・応答・PM 根拠を表示
- `/report` の該当銘柄に判定バッジを表示（Phase 2）

## 9. 非機能要件

| 項目 | 要件 |
|------|------|
| 縮退動作 | エージェント 1 体の失敗は「欠席」として PM に伝え、審議を続ける。アナリスト 2 体以上 + PM が揃わない場合は `failed` とし、通知には既存の内容のみ載せる |
| 冪等性 | 同日・同バッチ・同銘柄は再実行でも API を呼ばない |
| 構造化出力 | JSON パース失敗時は 1 回だけ再要求し、それでも失敗なら当該エージェントを欠席扱いにする |
| 温度 | 0.2〜0.3（再現性優先） |
| ログ | 全呼び出しのトークン数・レイテンシ・推定コストを保存する |
| 有効化 | `config.json > committee.enabled`（既定 false）。false の間は既存 `llm_advisor` の動作を維持し、いつでも戻せる |
| テスト | LLM 呼び出しをモックした単体テスト（既存 `test_llm_advisor.py` の方式）。プロトコル分岐（全員弱気で応答スキップ、欠席、予算超過、JSON 失敗）を網羅する |
| 免責 | Slack・ダッシュボードの委員会出力に免責文を付す |

## 11. 将来構想

Phase 1〜3 は下表の **Tier 1（PoC）** に相当する。以降の拡張は、前段の KPI を満たした場合にのみ進める（「作れるから作る」を避け、効果が確認できた分だけ投資する）。

### 11.1 スケール段階（Tier）

| 区分 | 初期開発費（目安） | 月額運用費（目安） | 規模・機能範囲 | 本システムでの位置づけ |
|------|------------------|------------------|---------------|---------------------|
| **Tier 1: PoC** | 0〜50 万円 | 1 万〜3 万円（本計画では LLM 費 1,000 円/月に圧縮） | 主要 5〜10 銘柄、エージェント 3〜5 体、Slack/Web 出力 | **Phase 1〜3（現計画）**。既存基盤の流用で初期費はほぼ実装工数のみ |
| **Tier 2: 社内プロダクト / SaaS MVP** | 300 万〜800 万円 | 10 万〜50 万円 | 数百銘柄の定時バッチスキャン、多段階ディベート、ダッシュボード | 運用資金の拡大、または外部提供による収益化が見込める場合のみ検討 |
| **Tier 3: エンタープライズ / 商用** | 1,500 万〜5,000 万円+ | 100 万〜数百万円 | リアルタイムデータ（Bloomberg 等）、高度 RAG、自動監視・連携 | 個人運用の範囲外。参考として記載 |

**コスト回収の目安**: 月額運用費を超過リターンで回収するには、概ね `月額運用費 ÷ 運用資金` の月次超過リターンが必要になる（例: 月 10 万円の運用費を月 2% の超過リターンで回収するには運用資金 500 万円）。Tier 2 以上は自己資金の運用だけでは回収が難しく、外部提供による収益化が前提になる。

### 11.2 Tier 移行の判断基準

| 移行 | 条件（すべて満たす） |
|------|------------------|
| Tier 1 継続 → 機能拡張（11.3） | KPI 1 で委員会 GO の期待値が全シグナルを上回る傾向がある / 月額 LLM 費が予算内 / 開催率 90% 以上 |
| Tier 1 → Tier 2 | 上記を 6 か月以上維持 / 運用資金または外部収益で月額運用費を回収できる見込みがある / 11.6 の法規制を確認済み |
| 停止判断 | 3 か月評価で委員会 GO と全シグナルに差がない、または下回る場合は委員会を停止し、既存 `llm_advisor` に戻す |

### 11.3 機能拡張ロードマップ（Tier 1 の範囲内）

KPI が良好な場合に、費用対効果の高い順に着手する。

| 優先度 | 拡張 | 内容 | コスト影響 |
|-------|------|------|----------|
| 高 | オンデマンド審議 | Prompt Builder / Screening から任意銘柄を委員会にかける（ボタン 1 つで実行、結果は `/committee` に保存） | 実行した分のみ |
| 高 | AiNewsDigest 連携 | 保有・監視銘柄に関するニュースを AiNewsDigest から自動収集し、マクロ/ファンダの入力に追加（`memo.txt` の拡張案） | 小 |
| 高 | エージェント成績の追跡 | エージェントごとの stance と実際の結果の一致率を記録し、`/committee` に表示。成績に応じて PM に渡す重みを調整 | なし（集計のみ） |
| 中 | マクロ指標の拡充 | FRED API（無料）で米金利・イールドカーブ・CPI 等を取得し、マクロエコノミストの入力を数値化 | なし |
| 中 | 動的ラウンド | 意見が大きく割れた場合（例: 強気と弱気が拮抗）のみ Round 3 を 1 回追加。上限ターン数は固定 | 対象銘柄のみ増 |
| 中 | ペルソナ追加 | センチメント・アナリスト（ニュース/SNS の論調）、セクター専門家（業種別の観点）を任意で追加 | 1 体あたり銘柄×1 呼び出し |
| 中 | 開示資料 RAG | EDINET（有価証券報告書）・TDnet（決算短信）を取得し、ファンダ・アナリストが根拠を引用できるようにする | 埋め込み費用 + 入力トークン増 |
| 低 | 監視銘柄への拡大 | moomoo お気に入り（毎時監視）でシグナルが出た銘柄も審議対象に追加 | 銘柄数に比例 |
| 低 | 週次ポートフォリオ審議 | 個別銘柄ではなく、保有全体の配分・集中度・相関を週 1 回審議 | 週 1 回分 |

### 11.4 技術面の将来構想

| 項目 | 現計画 | 将来の選択肢 | 移行のきっかけ |
|------|-------|-------------|--------------|
| オーケストレーション | 自前の軽量実装（固定 2 ラウンド） | LangGraph（条件分岐・状態管理・チェックポイント・可視化）。CrewAI / AutoGen はロール定義による迅速な試作向き | 動的ラウンドやエージェント数が増え、分岐が自前コードで追いにくくなった時点 |
| データソース（価格） | EODHD / yfinance / moomoo | Alpha Vantage、Financial Modeling Prep、Tier 3 では Bloomberg 等 | yfinance の欠損・仕様変更が頻発した場合、またはリアルタイム性が必要になった場合 |
| データソース（財務） | yfinance / J-Quants | Financial Modeling Prep、J-Quants 有料プラン | yfinance 財務の充足率が実用に満たない場合 |
| データソース（ニュース） | Google News RSS | News API、AiNewsDigest | ニュースの網羅性・鮮度が判定の弱点と分かった場合 |
| モデルルーティング | 軽量（アナリスト）/ 高性能（PM）の 2 層 | リスク評価にも高性能モデル、判定の割れ具合に応じて動的に高性能モデルへ切替 | 予算に余裕があり、PM 以外の品質がボトルネックと分かった場合 |
| 実行頻度 | 1 日 2 回のバッチ（寄り付き前 / 引け後） | 毎時監視連動、Tier 3 ではイベント駆動（決算・急変時） | 日中の判断遅れが損失につながる事例が蓄積した場合 |

### 11.5 Phase 1 で備えておくこと（将来構想のための拡張点）

将来の拡張で大きな作り直しにならないよう、Phase 1 の設計に以下を含める。

- **エージェント定義を設定駆動にする**: `config.json > committee.agents` にエージェント名・プロバイダー・モデル・有効/無効を持たせ、ペルソナ追加をコード変更最小で行えるようにする。
- **プロバイダー呼び出しを 1 関数に集約する**: 既存 `llm_advisor` の `_call_openai` / `_call_anthropic` / `_call_gemini` を共通インターフェースで呼べる形にし、モデルルーティングの変更を設定だけで済ませる。
- **エージェント単位でログを残す**: `agents_json` にエージェントごとの stance・confidence・トークン数を保存し、将来の成績追跡・重み付けに使えるようにする。
- **出力スキーマにバージョンを持たせる**: `schema_version` を JSON に含め、ラウンド追加やスキーマ変更後も過去ログを読めるようにする。
- **審議対象の投入口を 1 つにする**: バッチ・オンデマンド・監視銘柄のいずれからも同じ関数（例: `run_committee(subjects, context)`）で審議できるようにする。

### 11.6 外部提供（SaaS 化）時の留意点

Tier 2 以上で外部提供による収益化を検討する場合、技術以外の論点が大きい。

- **法規制**: 個別銘柄の売買判断を有償で第三者に提供する行為は、金融商品取引法上の投資助言・代理業の登録が必要になる可能性が高い。着手前に専門家へ確認する。
- **データライセンス**: yfinance（非公式）や個人向けプランのデータは再配布・商用利用が制限される場合が多い。商用ライセンスの費用が月額運用費の大半を占める可能性がある。
- **責任範囲**: 判定の誤りによる損失の扱い、免責表示、監査ログ（`committee_verdict_log`）の保存期間を定める必要がある。

## 12. リスクと未確定事項

- **yfinance 財務情報の信頼性**: 非公式 API のため欠損・遅延・仕様変更のリスクがある。JP 銘柄（`.T`）の項目充足率は Phase 1 で実測する。
- **J-Quants 無料プランの配信遅延**: ファンダ・アナリストへ渡す際にデータ日付を必ず明記する。
- **LLM の同調傾向**: Round 1 の独立性を守っても PM が多数派に寄る可能性がある。`dissent` を必ず記録し、Phase 3 で「少数意見が正しかった率」を確認する。
- **評価期間中のサンプル数**: 1 日 4〜5 銘柄 × 60 営業日 ≒ 250〜300 判定。統計的に強い結論は出にくいため、Phase 3 は「傾向の確認」と位置づける。
- **モデル価格の変動**: 推定コストは設定単価ベース。実請求額と月次で照合する運用が必要。
- **既存 `llm_advisor` の扱い**: Phase 1 では並存させ、委員会が安定した後に廃止を判断する。
